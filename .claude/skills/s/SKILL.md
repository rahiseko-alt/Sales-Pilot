# s — セッション開始の儀式

利用者は非エンジニア。前回どこまで進んだか、いま何が危険かを自分では判断できない。
このスキルが、開始時にその3点を代わりに提示する。

起動する場面と、一文字が別の意味に見えるときの扱いは
`docs/agents/flow-map.md`「セッションの開始と終了」が正。ここでは繰り返さない。

**自動で出すのは、そのセッションでまだ一度も出していない場合だけ。**
中断からの再開や文脈の圧縮で規則が読み直されても、二度目は出さない。

## 手順

### 1. 調べる（読むだけ。書き込まない）

- `docs/agents/handover.md` の**一番上の1件** … 前回の「次にやること」と「未解決の問題」
- `git status --short --branch` … 手元に未保存の変更があるか
- 送信済みかどうか … `f` スキルの「未送信の記録がゼロ」と同じ手順で判定する
- 提出中の変更（PR）があるか … `docs/agents/issue-tracker.md` の手順に従う。
  `gh` が無い環境では GitHub の MCP ツールを使う。
  **コマンドが失敗したことを「提出物は無い」と読み替えない。**
  確認できなかったときは「確認できませんでした」と書く。

### 2. 「最初の一手」は `next-step` に決めさせる

現在地の判定と次の一手の決定は `next-step` スキルの役目。
`s` がそれを独自に判断すると、二つの案内が食い違う。
調べた内容を渡して `next-step` を起動し、その結論を「最初の一手」に載せる。

### 3. 報告する

次の3点だけを、この順で、簡潔に出す。表は使わない。
（`flow-map.md`「説明の書き方」の3ブロックではなく、この型を使う。同節に明記された例外。）

1. **前回の続き**: 残っている作業を1〜2行。無ければ「ありません」と書く
2. **いまの状態**: 未保存の変更／未送信の記録／提出中の変更の3つを、有無がわかる形で1行
3. **最初の一手**: `next-step` が出した一手を1つだけ。利用者の操作が要るならその手順

例:

> **前回の続き**: 案内役が引き継ぎメモを読むかの確認が残っています。
> **いまの状態**: 未保存なし／未送信なし／提出中の変更なし。
> **最初の一手**: その確認を行います。始めてよろしいですか。

### 4. 報告したら止まる

報告は報告で終える。利用者の指示を待つ。
ただし**読むだけで済む確認**（ファイルを見る、状態を照会する）であれば、
その場で行って結果を報告に添えてよい。ファイルの変更・コミット・送信は行わない。

利用者が短い用件で開いた場合も報告は出す。報告を先頭に置き、そのあと用件に答える。
