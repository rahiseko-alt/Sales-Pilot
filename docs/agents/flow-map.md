# 開発フロー ナビゲーション（セッション開始時に自動読み込み）

このリポジトリのユーザーは非エンジニアの可能性がある。
`/grill-with-docs` などのコマンドを自分で選べる前提を置かないこと。

## セッションの開始と終了（最優先）

- **会話開始後の最初の応答では、冒頭で `s` スキルを起動する。** 利用者が何も打たなくても出す。
  前回の続き・いまの状態・最初の一手の3点を報告してから、利用者の用件に答える。
- 利用者が「s」「S」「/s」とだけ送ったら `s` スキルを起動する。
- 利用者が「f」「F」「/f」とだけ送ったら `f` スキルを起動する。
  この作業環境を破棄しても問題ない状態まで片づけ、根拠つきで終了可否を宣言する。
- 一文字が明らかに別の意味に見える場合は通常どおり応答する。迷ったときだけ一度だけ尋ねる。

## あなたが守ること

1. 実装（コードの新規作成・機能追加）を頼まれ、まだフローを通っていないなら、
   **コードを書く前に** `next-step` スキルを起動し、次に打つべきコマンドを1つ提示する。
2. 「何をすればいい」「次は」「どう進める」と聞かれたら `next-step` を起動する。
3. 各スキルが終わった直後にも `next-step` を起動し、次の一手を提示する。
4. ユーザーが「今はいい」「そのまま作って」と言った場合のみ、フローを飛ばしてよい。
   ただし飛ばした場合でも、コードを書く前に自分で `CONTEXT.md`（無ければ `CONTEXT-MAP.md` 経由で
   各コンテキストの `CONTEXT.md`）と、該当範囲の `docs/adr/`（多コンテキストなら
   `src/<context>/docs/adr/` も）を確認する。読んだ内容が今回の依頼と食い違えば、提案の前に
   一言伝える。用語集や決めた理由を読む役目は、通常はフロー内の各部品（`/to-spec` 等）が
   内蔵しているが、フローを飛ばすとその内蔵チェックごと消える。ここで代わりに行う
   （詳細は `docs/agents/domain.md` にもあるが、そちらが失われていてもこの1行で足りる）。
5. セッションの開始と終了は上の「セッションの開始と終了」に従う。`s` と `f` はこの一覧より優先する。
6. `/code-review` を実行するときは、対象範囲の `docs/adr/` の中身を、Standards 軸のサブエージェントへの
   指示文に**そのまま貼り付ける**（`CODING_STANDARDS.md` 等と並べて）。矛盾があれば「判断が割れる点」
   ではなく「違反」として扱わせる。`/code-review` 自身はこれをしないため、ここで渡さないと、
   決めた理由を記録しても検査されないまま流れる（詳細は `docs/agents/domain.md`「Feed `/code-review`'s
   Standards axis」にもあるが、そちらが失われていてもこの1行で足りる）。
7. `/setup-matt-pocock-skills` を実行するときは、`docs/agents/domain.md` や `issue-tracker.md` を
   書く前に**現在の中身を読む**。ベンダー配布のひな形（`.claude/skills/setup-matt-pocock-skills/*.md`）
   に無い節がこのリポジトリ側で足されていたら、それは後から直した穴埋めの可能性が高い。
   無条件の上書きはせず、その節を残したまま必要な変更だけを反映し、消える節がある場合は
   利用者に一言断ってから進める。

## フロー早見

- 新規開発・機能追加: `/grill-with-docs` → `/to-spec` → `/to-tickets` → `/implement` → `/code-review`
- 設計改善: `/improve-codebase-architecture` → 候補選択 → `/grill-with-docs` → 以下同じ

入口は `/grill-with-docs` の1つだけ。コードが無い段階でも同じものを使う。

詳細は AGENTS.md の「Development flow」を参照。

## 説明の書き方（既定）

ユーザーは非エンジニア。専門用語をそのまま出さない。

すべての報告・提案を、次の3ブロック・この順で書く。

1. **結論**（1行）: 何がどうなったか。相手が取るべき行動があるならそれも。
2. **理由**（2〜3行）: なぜそうなったか、何が起きているか。技術用語は日常語に置き換える。
3. **次**（1行）: 次に何が起きるか、または相手に選んでほしいこと。

置き換えの例:

| 使わない | 使う |
| --- | --- |
| CI / check run | 自動チェック |
| draft PR | 下書きとして提出した変更 |
| マージ可否 / mergeable | 既存のものと衝突していないか |
| レビューコメント | 指摘 |
| フック / SessionStart | 会話を始めるたびに自動で動く仕組み |
| スキル | 部品 / 案内役 |
| リポジトリ | この置き場所（文脈上必要なときのみ） |

**例外**: `s` と `f` の報告は、それぞれのスキルが定める型（3点／宣言＋確認項目の一覧）を使う。
儀式の報告はこの3ブロックに当てはめない。それ以外の報告はすべてこの節に従う。

守ること:

- 事実と推測を混ぜない。確証が無いことは「わからない」と書く。
- 確認コマンドが失敗したことを「問題なし」と読み替えない。確認できなければ「確認できませんでした」と書く。
- 相手が判断できない選択肢を並べない。おすすめを1つ先に出す。
- 短くする目的で結論だけにしない。理由を必ず添える。

## 引き継ぎメモ（毎回必ず書く）

セッションの作業環境は毎回消える。会話の内容は次回に残らない。
残るのは `docs/agents/handover.md` に書き、コミットして送ったものだけ。

### 書く場面（この2つだけ）

1. 何かを完成させて提出したとき（コミット・PR作成・マージなど、成果が形になった時点）
2. 方針を決めたとき（設計や進め方の合意ができた時点）
3. `f`（セッション終了の儀式）を実行したとき。ただし今回のセッションに書くべき成果や決定がある場合のみ

雑談や調査の途中では書かない。何も無かったセッションでは `f` でも書かない。

### 手順

1. `docs/agents/handover.md` の**一番上**（ヘッダの `---` の直下）に1件足す。書式は下記のとおり固定。
2. `sh .claude/hooks/handover-trim.sh` を実行して件数を上限まで削る。
3. 作業中の枝にコミットして送る。枝が無ければ既定の枝へ直接送る。承認を待たない。
4. 「引き継ぎメモに記録しました」と1行だけ利用者に伝える。

### 書式（崩すと自動読み込みが壊れる）

- 1件の区切りは行頭の `## `。日付と一言の見出しにする（例: `## 2026-09-09 引き継ぎメモの仕組みを追加`）。
- 中身は「決めたこと」「次にやること」「未解決の問題」の3項目のみ。
  そう決めた理由や触ったファイルは書かない（それは `docs/adr/` の役目）。
- 「次にやること」は、そのとおり実行しても壊れない順序で書く。
  例えば枝を消す手順を書くなら、その前に取り込む手順を必ず書く。

### 件数

保存の上限と、会話開始時に読み込む件数は `.claude/hooks/session-start.sh` の先頭で定義している。
数字はそこが正であり、この文書や README に書き写さない。
上限を超えると会話開始時に警告が出る。

上限を超えて押し出された分は消えない。`.claude/hooks/handover-trim.sh` が
`docs/agents/handover-archive.md` へ移す（会話開始時には読み込まれない。過去の経緯を
掘り返すときだけ、その中を検索・閲覧する）。
